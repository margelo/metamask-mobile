WebSocket Performance Benchmark
NitroWebSocket vs. React Native WebSocket — On-Device Results

Run date: 2026-06-30 16:24 UTC   |   Endpoint: ws://localhost:18765 (local echo server)
Runtime: React Native (simulator), both implementations are production code paths   |   Samples: n = 10–20 per scenario


SUMMARY

NitroWebSocket is faster on 8 of 9 app surfaces, ties on 1, and loses only on a single one-off tiny fetch. The gains fall into two buckets:

- Raw speed: big payloads (charts) and high-frequency streams (prices, orderbook) run roughly 2x–5x faster, even at the typical case.
- Consistency: on reconnect, batch subscribe, and first paint, React Native's bridge stalls for tens-to-hundreds of milliseconds. Nitro removes those stalls — this is the jank/freeze users actually feel.

Headline numbers:

| Metric                     | React Native | Nitro       | Speedup |
|----------------------------|--------------|-------------|---------|
| Reconnect recovery (mean)  | 74.9 ms      | 5.4 ms      | 13.95x  |
| Batch subscribe (mean)     | 8.7 ms       | 1.6 ms      | 5.53x   |
| Charts, graph load (mean)  | 4.8 ms       | 0.9 ms      | 5.20x   |
| RTDS price stream          | 8,097 msg/s  | 18,383 msg/s| 2.27x   |
| Predict price stream       | 7,359 msg/s  | 14,959 msg/s| 2.03x   |

Where it does not win: one-off tiny first-fetches (RTDS time-to-first-price, 0.38x), where Nitro's fixed ~0.6 ms per-call overhead cannot be amortized. Heartbeat round-trip is a dead tie (1.00x).

Caveat: measured on localhost against a simulator. Read these as a relative per-feature comparison, not absolute production latency. Small sample sizes mean single-spike tails are directional, not precise.

How to read the consistency wins: at the median these are near-ties, but React Native's tail is severe — reconnect p95 446 ms, batch p95 42.6 ms, ticker p99 27.2 ms. Nitro's tails stay tight (14 ms / 1.67 ms / 1.96 ms). That tail is the freeze users feel.


THE THREE BIGGEST WINS

1. Reconnect recovery — 13.95x. React Native stalls to 446 ms worst-case; Nitro stays at 14 ms. Removes the freeze when the app resumes or reconnects.
2. Batch subscribe — 5.53x. React Native tail 42.6 ms; Nitro 1.67 ms. Faster, smoother Predict homepage load.
3. Charts, graph load — 5.20x. 4.8 ms to 0.9 ms, faster at the median too. The cleanest pure-speed win (big payloads favor Nitro).


TWO KINDS OF WINS

Raw speed (faster even at the typical/median case):
- Charts, graph initial load: 4.0 ms to 0.9 ms median (~4.5x) — standout
- Perps orderbook, per update: 0.143 ms to 0.086 ms median (~1.7x)
- Predict orderbook, per update: 0.115 ms to 0.080 ms median (~1.4x)
- Predict price stream throughput: 7,359 to 14,959 msg/s (2.03x)
- RTDS price stream throughput: 8,097 to 18,383 msg/s (2.27x)

Consistency (median near-tie, but Nitro removes the ugly tail spikes):
- Reconnect recovery: RN p95 446.5 ms vs Nitro 14.0 ms → mean 13.95x
- Batch subscription: RN p95 42.6 ms vs Nitro 1.67 ms → mean 5.53x
- Predict price ticker, 1st: RN p99 27.2 ms vs Nitro 1.96 ms → mean 2.32x


WHY THE PATTERN LOOKS LIKE THIS

- Big payloads (charts, 500-point series): the bridge must serialize the whole blob to a string and copy it across threads; cost scales with size. Nitro's zero-copy JSI path does not — the bigger the message, the bigger the win.
- High-frequency streams (orderbook, prices): per-message bridge overhead multiplies across hundreds of messages per second; Nitro removes it every time.
- Tail spikes (reconnect, batch): the bridge batches work and competes with other JS-thread traffic and garbage collection, producing occasional large stalls. Nitro's direct path sidesteps the queue, so worst-case stays bounded.
- One-off tiny first-fetch (RTDS time-to-first-price): nothing to amortize Nitro's fixed per-call setup against, so the lightweight bridge path can win.
