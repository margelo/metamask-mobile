--------------------------------------------------------------------------------
  HEADLINE: THERE IS NO 100x–500x. NOT EVEN CLOSE.
--------------------------------------------------------------------------------

  The biggest real win here is 2.53x (and that one is a tail-latency effect,
  not a median win). In several scenarios NitroWebSocket is actually SLOWER.
  This is the honest picture the modelled 477x/497x lab numbers could not show.

  Why so different from the lab run?
    - Real implementations have real fixed costs. Nitro's JSI call + adapter
      event dispatch adds ~0.5–0.6 ms per discrete operation. The lab model
      assumed Nitro overhead = 0.
    - Localhost echo = near-zero network, so these are best-case for ratios,
      yet they still stay tiny because the per-op costs are comparable.
    - Simulator runs on a fast Mac CPU, which shrinks the bridge penalty
      relative to a real phone.

--------------------------------------------------------------------------------
  THE REAL PATTERN (this is the useful finding)
--------------------------------------------------------------------------------

  Nitro adds a small FIXED cost per discrete operation, but is more EFFICIENT
  per message in bulk. So the winner flips depending on the workload:

  WHERE NITRO WINS — bulk / high-frequency message processing
    - Price stream throughput : 1.52x  (7,293 -> 11,063 msg/s)
    - Orderbook burst per-msg  : 2.04x  (0.198 -> 0.097 ms)
    - Heartbeat tail latency   : far tighter p95 (10.5 ms -> 1.0 ms)
    When many messages flow, Nitro's zero-serialisation per-message path pulls
    ahead and its tail is much smoother (no bridge-batch / GC spikes).

  WHERE NITRO LOSES — single-shot / connection-establishment operations
    - Cold-start (1 msg)       : 0.45x  (Nitro +0.66 ms)
    - Batch subscribe (1 msg)  : 0.35x  (Nitro +0.59 ms)
    - Reconnect (connect+1 msg): 0.70x  (Nitro +1.59 ms)
    For one-off operations there's no bulk to amortise Nitro's fixed JSI/adapter
    setup cost, so the lightweight bridge path is actually quicker here.

  Mental model:
    Few messages  -> fixed overhead dominates -> RN bridge can win.
    Many messages -> per-message efficiency dominates -> Nitro wins + smoother.


--------------------------------------------------------------------------------
  HONEST CAVEATS
--------------------------------------------------------------------------------

  - Simulator, not a real phone. A real (esp. low-end Android) device makes the
    bridge more expensive, which would shift results toward Nitro. Re-run on
    hardware before drawing final conclusions.
  - Localhost echo, not real servers. Add real network latency (tens of ms,
    paid by both) and ALL these ratios compress further toward 1.0x.
  - Small samples (n=10–20). The 10.484 ms heartbeat p95 and similar tails are
    likely one-off GC/scheduler spikes, not stable signal. Increase n for
    publishable numbers.
  - Echo round-trips, not production subscribe/stream patterns. The new
    "subscribe" mode against real Predict/RTDS endpoints will be more
    representative still.


--------------------------------------------------------------------------------
  WHAT TO ACTUALLY CLAIM
--------------------------------------------------------------------------------

  - NitroWebSocket's real advantage is high-frequency throughput (~1.5–2x) and
    much tighter tail latency (smoother UI, fewer jank spikes on busy feeds).
  - It is NOT a universal speedup: for one-off connects/subscribes it can be
    marginally slower due to fixed per-call overhead.
  - The "hundreds of x" numbers were a loopback + modelled-bridge artifact and
    should not be quoted. These on-device numbers are the ones to trust.
